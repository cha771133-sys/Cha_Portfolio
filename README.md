## 논문

### API Gateway 성능 비교 연구 (소논문)
> MSA 환경에서 Nginx(OpenResty), Kong, Spring Cloud Gateway를 JWT(RS256) 인증 및 트래픽 스파이크 상황에서 비교

- **문제 정의**: MSA에서 API Gateway는 모든 요청의 단일 진입점이라 시스템 전체의 지연과 안정성을 좌우합니다. 실무에서는 모든 요청에 JWT 서명 검증이 붙고 트래픽 스파이크도 빈번하지만, 기존 비교 연구는 일정한 부하에서 라우팅 성능만 측정했을 뿐 JWT 인증 부하와 트래픽 스파이크를 동시에 반영한 비교가 부족했습니다.
- **담당 역할**: 단독 연구 — 실험 환경 구축, 실험 설계, 벤치마킹, 결과 분석 (백엔드 서버 2개 구현, Nginx JWT 검증 로직 직접 구현, Prometheus·Grafana 모니터링 구성 포함)
- **기술적 의사결정**: 서로 다른 동시성 모델의 대표로 Kong(API Gateway 기준점), Nginx(싱글 이벤트 루프/비동기), Spring Cloud Gateway(JVM 스레드 풀/동기)를 선정. CPU 집약적인 RS256 서명 검증으로 Gateway 간 부하 차이를 드러내고, Docker Compose로 동일 조건(메모리 1GB) 구성 후 k6로 Baseline→Spike→Recovery 부하를 생성.
- **트러블슈팅**: ① SCG 메모리 병목 — 512MB에서 JWT 검증 시 실패율·지연 급증, 1GB로 재설정해 실패율 0%·p95 1.09s→794ms로 개선. ② Nginx JWT 구현 — lua-resty-jwt가 OpenSSL 3.x와 호환되지 않아 lua-resty-openssl로 직접 구현. ③ Nginx는 메모리를 늘려도 p95가 개선되지 않아(20.5s→23.45s) 자원 부족 가설을 기각하고 이벤트 루프 블로킹을 구조적 원인으로 가설 수립.
- **성과**: JWT 적용 시 Kong p95 1.9ms(실패율 0%), SCG 794.64ms(0%), Nginx 23.45s(0.08%). Kong이 가장 안정적, SCG는 개별 속도는 느리나 스파이크에 안정적, Nginx는 JWT+스파이크 결합 시 가장 불안정. (구조적 원인은 가설 단계, CPU 관측·HS256 대조 실험이 후속 과제)
- **기술 스택**: Nginx(OpenResty), Kong, Spring Cloud Gateway, Docker Compose, k6, Prometheus, Grafana, JWT(RS256)

## 학교활동

### 안심집 (GDGoC)
> 공공데이터 기반 1인 가구를 위한 관악구 동네 안전등급 분석 웹 서비스

- **문제 정의**: 집을 구할 때 가격·교통은 쉽게 확인하지만 "이 골목이 밤에 안전한가"에 답하는 서비스가 없습니다. CCTV·보안등·파출소·범죄 통계는 공개돼 있지만 부처별로 분산돼 일반 사용자가 조합하기 어렵습니다. 흩어진 공공데이터를 통합·점수화해 정보 비대칭을 해결합니다.
- **담당 역할**: 팀 5명(데이터 1, 백엔드 2, DB 1, 프론트 1) 중 데이터 담당. 공공데이터포털·서울 열린데이터광장에서 원시 데이터 수집, 관악구 대상 정제·필터링, 4개 데이터셋을 공통 스키마로 통합하는 CSV 파이프라인 설계.
- **트러블슈팅**: 서울시 가로등 데이터는 관악구 범위에서 219개만 확보돼 과소 집계되는 문제를 "관악구 보안등정보" 데이터셋으로 교체해 13,283개로 확대. 통합 후 변별력 없는 컬럼(cctv_pixel 99.7% 동일값, install_ym 100% 결측)을 제거.
- **성과**: (진행 중) 관악구 통합 안전데이터 CSV 완성 — 총 15,399행 (CCTV 2,106 / 보안등 13,283 / 파출소 9 / 범죄통계 1)
- **기술 스택**: Python, Pandas

### TrackLook — 카공족을 위한 지도 (Likelion)
> 성동구 카공족을 위한 카페 추천 서비스. 네이버 리뷰를 LLM으로 분석해 콘센트·와이파이·소음·눈치·테이블 5대 지표로 점수화

- **문제 정의**: 카공에 중요한 작업 환경 정보는 블로그 리뷰 곳곳에 흩어져 있어 일일이 읽지 않으면 알기 어렵고, "카공하기 좋다"의 기준도 사람마다 달라 판단이 쉽지 않습니다. 리뷰를 LLM으로 분석해 5개 지표로 세분화하고 사용자가 직접 필터링할 수 있게 했습니다.
- **담당 역할**: 팀 3명(PM 1, 프론트 1, 백엔드 1) 중 백엔드 담당. JWT 로그인/인증 DB 처리, 위치 기반 카페 검색, 리뷰 작성·조회·삭제 API, 카페 목록 필터링·정렬 API 구현, 발표용 시스템 아키텍처 작성.
- **기술적 의사결정**: Django REST Framework로 짧은 기간 내 REST API를 빠르게 설계하고 SimpleJWT로 인증을 구현. LLM 점수화는 리뷰 텍스트를 Qwen3.5:122b(Ollama, L40 GPU)에 넣어 4개 지표는 1~5점, 테이블 지표는 언급 자체가 적어 0/5점 이진으로 채점. 데이터 파이프라인은 카페 수집→리뷰 크롤링→LLM 채점→정보 보강의 Django management command로 설계.
- **트러블슈팅**: 마커 258개가 한 번에 떠 복잡한 문제를 우선순위 상위 30개만 표시하도록 조정. 이메일 기반 회원가입을 일정상 아이디/비밀번호 방식으로 단순화. 위치가 엉뚱하게 잡히는 문제는 발표·시연 화면에서 위치를 고정해 대응(정확도 개선은 후속 과제).
- **성과**: 3주 내 백엔드 API를 전부 구현해 발표·제출 완료. 성동구 카페 258개와 리뷰 3,693건을 수집해 LLM 5대 지표 점수화까지 완료.
- **기술 스택**: Django 6.0, DRF, SQLite, SimpleJWT, Kakao 로컬 API, 카카오맵 SDK, Naver 블로그 검색 API, Qwen3.5:122b

### 다시 봄 (Likelion 해커톤, 본선 진출)
> 완경기 여성의 흩어진 몸·마음·피부 신호를 AI로 연결해 생활습관으로 관리하는 헬스케어 서비스

- **문제 정의**: 완경기 여성은 증상이 반복돼도 데이터로 쌓이지 않고, 가족에게 말해도 공감받지 못해 고립되며, "병원 갈 정도인가"를 판단할 기준이 없어 병원행을 포기합니다. 몸·마음·피부 데이터를 엮어 "오늘 컨디션이 왜 이런지" 설명하고 일상 틈새에 자기 돌봄을 심어주는 서비스를 기획했습니다.
- **담당 역할**: 팀 5명(풀스택 1, 프론트 1, 챗봇 1, 얼굴 분석 1, 증상 분석 1) 중 풀스택 담당. 복약·영양제, 명상·스트레칭 알림 도메인을 설계·구현하고, 흩어져 있던 각 앱의 인증을 JWT 기반 실제 로그인 사용자(request.user) 기준으로 통합하는 리팩토링 담당.
- **기술적 의사결정**: 리마인더 API는 전체 교체(PUT)가 아닌 부분 수정(PATCH)만 허용. 완료 상태는 boolean 필드 대신 "완료 기록 존재 여부"로 표현해 같은 엔드포인트 호출만으로 토글되게 설계. 시연 시드 데이터는 난수 시드를 고정해 몇 번을 돌려도 같은 패턴이 나오도록 구성.
- **트러블슈팅**: 인증 구조를 JWT 기반으로 리팩토링하면서 다른 팀원의 챗봇 테스트가 기존 가정으로 짜여 있어 8개가 401로 깨짐. force_authenticate로 보완해 해결했고, 여러 사람이 건드리는 공통 구조는 변경 범위를 미리 공유해야 한다는 걸 체감.
- **성과**: 순천향 Likelion 해커톤 본선 진출. 알림 도메인과 전체 서비스 인증 통합을 담당해 팀원들의 기능이 하나의 일관된 인증 체계 위에서 동작하도록 기여.
- **기술 스택**: Django, DRF, PostgreSQL, React Native(Expo), Gemini API, JWT

### 약속 (Promise)
> 시니어를 위한 AI 복약 관리 시스템. 처방전 사진 한 장으로 복약 알림을 자동 등록하고, 브라우저를 닫아도 환자·보호자에게 텔레그램 알림 발송

- **문제 정의**: 고령층은 여러 약을 정해진 시각에 챙겨야 하지만 시간을 놓치거나 혼동하기 쉽습니다. 기존 앱은 약 이름·시각을 직접 입력해야 해 진입 장벽이 높고, 혼자 사는 어르신은 알림을 놓쳐도 확인해줄 사람이 없습니다. 처방전 사진으로 복약 정보를 자동 등록하고 보호자도 함께 알림받게 해 두 문제를 해결합니다.
- **담당 역할**: 개인 프로젝트 — 기획·설계·개발 전 과정 단독 수행. 처방전 OCR 파이프라인, 서버 사이드 스케줄 알림 아키텍처, 텔레그램 봇 연동, 보호자 정보 저장 구조를 직접 설계·구현.
- **기술적 의사결정**: 핵심은 "브라우저를 닫아도 알림이 가야 한다"는 요구. 클라이언트 타이머에 의존하면 앱을 끄는 순간 멈추므로 스케줄링을 서버 사이드로 이전. 상시 서버 대신 Upstash QStash(서버리스 cron)를 선택해, 분석 완료 시 복약 시각마다 cron을 등록하고 QStash가 /api/notify를 호출해 알림 발송. 처방전 인식은 Gemini Vision으로 OCR+약품 추출을 한 번에 처리하고 식약처 API로 교차 검증.
- **트러블슈팅**: QStash는 공개 URL만 호출 가능해 localhost에서는 전체 흐름 테스트가 불가능하고 서명 검증도 실패. 로컬에서는 /api/notify에 직접 POST해 발송 로직을 검증하고, QStash 연동 포함 전체 흐름은 Vercel 배포 환경에서 확인하도록 테스트 전략을 분리.
